# BrewLog 프론트엔드 분리 전환 검토 v1.0

## 1. 결론

현재 BrewLog는 단기적으로 `Thymeleaf + CSS + 필요한 JavaScript` 구조를 유지한다.

다만 다음 화면은 상태와 인터랙션이 빠르게 복잡해지고 있으므로, 중기적으로 Vue3 island 또는 React island 형태의 부분 도입 후보로 둔다.

1. 원두 등록 폼
2. 브루잉 기록 폼
3. 카페 필터커피 등록 폼
4. 카페 지도

전체 SPA 전환은 아직 이르다. 목록, 상세, 홈 화면은 서버 렌더링으로 충분하고, 현재 데이터 규모에서는 페이지 이동 비용보다 구현 복잡도 증가가 더 크다.

## 2. 현재 유지할 구조

| 영역 | 유지 방식 | 이유 |
|---|---|---|
| 홈 | Thymeleaf | 요약 데이터 렌더링 중심 |
| 원두 목록 | Thymeleaf | 검색, 탭, 카드 목록이 서버 렌더링과 잘 맞음 |
| 원두 상세 | Thymeleaf + 모달 JS | 상세 URL 유지와 모달 표시를 함께 지원 가능 |
| 브루잉 목록/상세 | Thymeleaf + 그래프 JS | 그래프만 클라이언트 계산이면 충분 |
| 카페 필터 목록/상세 | Thymeleaf + 모달 JS | 목록 필터와 상세 표시는 서버 렌더링으로 충분 |
| 카페 지도 | Thymeleaf + 지도 JS | 지도 상태가 커지면 island 후보 |

## 3. 분리 후보 화면

### 3.1 원두 등록 폼

분리 후보 이유:

- OCR 업로드, 결과 확인, 자동 채움, 수동 수정이 한 화면에 있다.
- 새 향미 노트 입력 시 LLM 색상 추천 대기 상태가 필요하다.
- 구매처 검색, 기존 구매처 선택, 지도 선택 상태가 서로 연결된다.

권장 방향:

- 단기: 현재 단계형 폼 유지
- 중기: `BeanFormIsland`로 폼 상태만 Vue3 또는 React로 분리
- API 후보: `POST /api/coffee-beans/card-extraction`, `POST /api/coffee-beans`

### 3.2 브루잉 기록 폼

분리 후보 이유:

- 푸어링 그래프 포인트 편집, 드래그, 누적 물량 계산이 클라이언트 상태 중심이다.
- 종료 시간과 포인트 시간이 1초 단위로 바뀌면서 그래프 재계산이 잦다.
- 단계 이동과 검증이 폼 내부 상태에 의존한다.

권장 방향:

- 단기: 기존 JS를 유지하되 푸어링 그래프 코드를 별도 파일로 분리
- 중기: `BrewRecordFormIsland`로 푸어링 그래프와 레시피 단계만 분리
- API 후보: `POST /api/brew-records`

### 3.3 카페 필터커피 등록 폼

분리 후보 이유:

- 카페 검색, 지도 선택, 기존 카페 중복 방지, 원두 자동 채움이 연결된다.
- 브루잉 레시피는 선택 기능이므로 조건부 UI가 많다.
- 카페별 기록 흐름과 지도 데이터가 같은 장소 모델을 공유한다.

권장 방향:

- 단기: Thymeleaf 폼 유지
- 중기: 카페 검색/지도 선택 영역만 `CafePlacePickerIsland`로 분리
- API 후보: `GET /api/purchase-places/search`, `POST /api/cafe-filter-coffees`

### 3.4 카페 지도

분리 후보 이유:

- 지도 줌, 지역 선택, 핀 선택, 바텀시트 상태가 모두 클라이언트 상태이다.
- 좌표 보정과 지도 투영 로직이 커지고 있다.
- 모바일과 데스크톱의 패널 배치가 크게 다르다.

권장 방향:

- 단기: 현재 `cafe-map.js` 유지
- 중기: `CafeMapIsland`로 지도와 정보 패널을 분리
- API 후보: `GET /api/maps/cafes`

## 4. 전환 판단 기준

다음 조건 중 2개 이상이 한 화면에서 동시에 발생하면 프론트 island 도입을 검토한다.

- 서버 재렌더링 없이 화면 상태를 3개 이상 동시에 관리해야 한다.
- 사용자의 한 조작이 2개 이상의 UI 영역을 동시에 갱신한다.
- 로딩, 실패, 재시도, 부분 저장 상태가 필요하다.
- 같은 클라이언트 컴포넌트를 2개 이상의 화면에서 재사용한다.
- JavaScript 파일이 한 화면에서 400줄을 넘고 테스트가 어려워진다.

## 5. 단계별 전환안

### Step 1. JavaScript 모듈 정리

- 인라인 스크립트를 기능별 정적 파일로 이동한다.
- `form-wizard.js`, `detail-modal.js`, `cafe-map.js`처럼 역할 단위 파일을 유지한다.
- 이 단계에서는 빌드 도구를 추가하지 않는다.

### Step 2. Vue3 island 또는 React island 도입

- 단일 화면의 복잡한 영역만 독립 마운트한다.
- 서버가 초기 데이터를 JSON으로 내려주고, island가 그 영역만 제어한다.
- 우선 후보는 카페 장소 선택 또는 푸어링 그래프이다.

### Step 3. API 정리

- 폼 저장, OCR 결과, 장소 검색, 지도 데이터 API DTO를 정리한다.
- Thymeleaf 화면과 island가 같은 API를 사용할 수 있게 한다.

### Step 4. SPA 전환 재검토

- 화면 대부분이 island가 되었을 때만 SPA 전환을 검토한다.
- 개인 로컬 앱 성격이 강하므로 라우팅, 인증, 배포 복잡도 증가를 반드시 비교한다.

## 6. 현재 권장 우선순위

1. Thymeleaf 유지
2. 인라인 스크립트 정적 파일 분리
3. 푸어링 그래프 모듈화
4. 카페 장소 선택 모듈화
5. 필요한 경우 Vue3 island 도입

지금 당장은 Vue3 또는 React로 전체를 갈아엎기보다, 복잡한 인터랙션을 작은 섬처럼 분리하는 쪽이 BrewLog의 개발 속도와 유지보수에 더 맞다.
